## Crash evidence (server side: exit reporter, POST /diag/upload, 1691 uploads reviewed)
Reasons: LOW_MEMORY at importance 400 = benign background kills (noise). Foreground SIGSEGV (SIGNALED 11, importance 100) are the real crashes.

### Family 1 (NEW in 2.11.800, ~44 % of foreground exits: 16 of 36 in ~14 h, 0 in earlier versions): SIGSEGV pc=0, fault addr 0, x16=0
* Timing: 1..4 s after `D/Unity GameScene`.
* Root cause (high confidence): libkfpatch watcher thread gave up. `src/native/kfpatch/kfpatch.c` polled `dl_iterate_phdr` for libil2cpp.so only 20 000 x 1 ms (~20 s) and then logged "libil2cpp.so not found, hooks disabled" and returned, leaving the slot table (libil2cpp RVA 0x4982C00) all zero. The 10 migrated prod caves are reached through static veneers in libil2cpp (`adrp x16,slot; ldr x16,[x16]; br x16`), so a zero slot is `br 0`: pc=0, x16=0, fault 0.
* Why libil2cpp can appear after 20 s: KfPatchProvider (initOrder 1000) loads libkfpatch in every process start. The ranked-search FCM push (KF_PUSH=1, RankedSearchNotifier) spawns the app process WITHOUT an Activity/Unity; libil2cpp is mapped only when the user later opens the game, after the watcher already quit. Correlated: API push log 08:40:15Z vs device process creation 14:10:15 local, followed by the pc=0 crash on the first battle. The release lib contains the string "libil2cpp.so not found, hooks disabled" (confirmed with `strings`).
* Fix (this change): watcher never gives up (1 ms steps for 20 s, then 20 ms steps until libil2cpp appears). Hook sites are battle-time code seconds after the mapping, so a <=20 ms fill delay is safe. Compiles with NDK 27.2.12479018 (not installed on a device, not published).

### Family 2 / "f18" (pre-existing: 9 in 2.11.800, 4 each in 2.11.705 and 2.11.706): SIGSEGV fault 0x18, thread UnityMain, after MatchingScene
* Local Run A (`.local/run/logcat-release-2.11.800-run1-crash.txt`, pid 16231): il2cpp base 0x71a544c2d000 (KFPATCH line) -> reported pc RVA 0x13EE484, x30 RVA 0x1564ACC (guest registers under ndk_translation).
* Root cause (high confidence): 0x13EE484 is the entry of the PHOTON_FLOW dispatcher patch in `scripts/patch-il2cpp-endpoints.py` (callback `NormalMatchingController.<>c__DisplayClass48_0.<GrpcGetAssignments>b__1(closure, GetAssignmentsResponse x1, state w2, gRPC StatusCode w3)`, invoked via `GRE.ActionExtensions$$Call` 0x1A1BC00). The patched code did `ldr x8,[x20,#0x18]` on the response WITHOUT a null check. On state Error/Cancelled/Completed (2/3/4) the response is null (x20=0) -> fault addr 0x18. Triggered by stream failures during matching: gRPC 13 (Internal, API restart / proxy reset) and 14 (Unavailable, network drop). Not kfpatch code.
* Evidence: 72 CRASH lines with x2/x3 recorded (state 2 and status 13 dominate). Crashes cluster 2.5-40 s after MatchingScene (Stage 1 window, before the 40 s roster). Correlated to the second with API restarts in api.log (Kestrel "Overriding address" / startup at 04:20:03Z, 05:47:57-58Z; earlier 04:19:53Z, 05:16:07Z, 05:33:42Z) and nginx `upstream prematurely closed connection` on `/openmatch.Frontend/GetAssignments`.
* Fix (this change, patcher only, no server change): replacement at 0x13EE484 is now `cbz x20,0x13EE4A4` (null response takes the original Cancelled/Completed handler = `GetAssignmentsDestroy(controller,false)`), then the previous dispatch (`ldr x8,[x20,#0x18]; cbz x8,0x13EE4D0; ldr x9,[x8,#0x18]; cbz x9,0x13EE4D0; ldr w9,[x9,#0x10]; cbnz w9,0x13EE4F8; b 0x13EE4D0`), still 32 bytes. Patcher output vs release lib differs only in 0x13EE484..0x13EE4A3 (byte-guards pass on the pristine lib, 239 reports). Trade-off: the retry-on-error behaviour (RetryGrpcGetAssignmentsAsync) is not restored; on a dropped stream the player returns to the previous screen instead of crashing.
* Family 3 (pre-existing): fault 0x7b0 in UnityMain: ROOT-CAUSED in 2.11.802, see "Family 3 (0x7b0)" at the end of this file.

### "Battle Start" freeze (coordinator report, cold start)
* UI mapping NOT proven. "Battle Start!" = `inGameTutorial.countDownMessage` (masters_translation id 362), "Remaining" = `common.remaining` (id 63, LoadManager.Remaincount, i.e. asset/scene loading). Server flow (BattleMatchmakingService.cs): Stage 1 on join, Stage 2 full roster after the 40 s window, 2 s delay, Stage 3 final assignment with Connection, then HoldFinalAssignmentAsync 30 s. The freeze most plausibly spans Stage 3 -> GameScene load (UnityMain busy), which is where family 1 fires (1.3-6 s after `D/Unity GameScene`).
* Family 1 timing check (17 pc=0 crashes, all 2.11.800): of the ones with known process start, 8 are late-activity (Activity 54..9148 s after process start, i.e. process spawned in background), 6 log "libil2cpp.so not found"; NONE has a known true cold start (<10 s); 9 have unknown start (pid-filtered log buffer lost the start). Cold starts with the base found (4) reached GameScene normally. Caveat: Android reuses a background-spawned process (FCM push, receiver, ContentProvider) when the user taps the icon, so the player perceives a "cold start" while the process is old and its watcher had already given up. Hence the cold-start report is compatible with family 1.
* Hook sites on the 10 migrated veneers: 0x13BEAEC (PlayerCharacter.UpdateAi), 0x13BC3A8 (PlayerBoneController.GetDisplayAngles), 0x1807474 / 0x18072D0 (AIPlayerEngine.UpdateTarget), 0x1808D40 (AIScrambleScoreEvaluationEngine.CalcScore), 0x1439AEC (BatAbilityParameter..ctor, the only `bl` hook), 0x17F8F1C (PlayerStateSkill.End), 0x184961C (SmogConditionAction.CreateSmog), 0x184983C (SmogConditionAction.Initialize), 0x1A2AC44 (PhotonPropertyManagerBase<GameManager>.CheckInitializeError). Names from the Il2CppDumper dump matched heuristically (dump-to-binary provenance unproven).
* x30 low12 of the pc=0 reports (rea-binary-researcher, direct `bl` analysis only): 0xaf0 = site 0x1439AEC (bl hook sets x30=0x1439AF0, path-independent match). 0x964 matches NO site through direct calls; remaining candidates need indirect callers (0x13BEAEC via ManagedUpdate, 0x17F8F1C End, 0x1A2AC44) and cannot be attributed without vtable/delegate analysis. So at least one pc=0 sub-case is the BatAbilityParameter ctor (battle/disc setup, i.e. load phase).
* 2.11.706 vs 2.11.800 patch-set diff not performed (2.11.706 had no kfpatch; family 1 absent there).

## Family 3 (0x7b0), 2.11.802 (2026-11-06)
Crash: SIGSEGV SEGV_MAPERR fault addr 0x7b0, thread UnityMain, ~18.6-26.4 s after `D/Unity: GameScene` (the "Battle Start!" countdown; a minority 3-6 s). 58 reports from the VPS /diag/upload (2.11.705/706/800, rate unchanged across versions, so it predates libkfpatch) plus the local emulator repro `.local/run/logcat-release-2.11.6-gate-battle1-crash.txt` (2.11.6 gate, 10:00:44). The "libunity+0x34426c" in the backtrace is the ndk_translation artifact; the real fault is in the third-party CRIWARE plugin.
* Fingerprint (identical in production reports, in the 2.11.6 repro and in the synthetic repro below): x0=x8=x20=0, x9=0x30, x21=0x68, pc low12 0xd28, lr low12 0xcf4, x19-pc = 0x16b2d8 (x19 = adrp base of the CRI `.bss` page).
* Native site: `libcri_ware_unity.so` file/RVA 0x59cd8 (static fn reached from `criAtomExSoundObject_Create+100`), crash at 0x59d28 `ldr w0,[x8,#0x7b0]` with x8 = `[.bss 0x1c5590]` = NULL. `.bss 0x1c5590` is the ACF state (allocated 0xe80 B in the register path at 0x58930-0x589a8, set to NULL in the unregister path 0x589d0-0x589e8); `.bss 0x1ca58c` is the "ACF registered" flag (written by `criAtomEx_RegisterAcfData` 0xb5848, cleared by `criAtomEx_UnregisterAcf` 0xb5cf0 @0xb5e20; the guard function 0xb5cac returns it, message "E2010091600:ACF is not registered."). The function at 0x59cd8 reads `g->0x7b0` without a null check when the flag is 0. => CRIWARE has NO ACF registered when the Battle Start voice creates a 3D sound object.
* Managed chain: `GameStartPresenter.Update` -> `PlayerCharacter.PlayVoice3d` (0x13D8C00) -> `AudioManager.PlayVoice3d` -> `Play3d` -> `GetSourceVoice3d` -> `AddVoice3d` (0x1BDBA18) -> `AudioManager.CreateSoundObject` (0x1BDBEFC, the only caller of `CriAtomExSoundObject..ctor` 0x271EC14) -> `criAtomExSoundObject_Create`. 3D voices are the first battle-time CRI call that dereferences the ACF state unchecked (other CRI calls log E2010091600 and return), so the crash shows up there.
* Why the ACF is unregistered on those clients: NOT proven. ACF/ACB/AWB are not in the APK; all audio config is Octo-delivered (`cri-config-acf` = colorful.acf, `/cdn/v9pkqH`, in config/resources/title-minimum.json and catalog.json). In the 2.11.6 repro CRIWARE initialised at boot (libcri_ware_unity loaded, OpenSL AudioTrack created 09:53:59), so the state was lost or never established later. A 2026-09 finding (docs/CONTINUATION_PROMPT_BATTLE_CRASH_FIX_V2.md 7.1) showed unseeded Octo caches crash 3/3 with 0x7b0 and seeded ones do not, which makes "ACF/audio bundles missing or incomplete in the device Octo cache" the leading hypothesis (medium confidence); finalize-on-scene-change and init failure are not excluded. Crash rate vs total battles is unknown.
* Natural repro: none (the emulator caches are complete). Synthetic repro with the same fingerprint: build with `KF_CRI_TEST=1` (hooks_cri.c zeroes the ACF state pointer and flag for the duration of the CreateSoundObject call, guard off): `.local/run/logcat-802-test1.txt` 11:07:06 `KFPATCH: TEST1 ...` then `signal 11 ... fault addr 00000000000007b0`, pc 0x71a49abead28 (cri+0x59d28), lr ...acf4, x19-pc 0x16b2d8, x0=x8=x20=0, x9=0x30, x21=0x68.
* Fix (2.11.802, libkfpatch only, no server change): slot 8 trampoline over `AudioManager.CreateSoundObject` 0x1BDBEFC (12 bytes `f44fbea9 fd7b01a9 fd430091` -> `adrp x16,slot; ldr x16,[x16,#0xc40]; br x16`, PC-independent per kfpatch_tramp.py) -> `hook_csobj` in `src/native/kfpatch/hooks_cri.c`: if `[cri_base+0x1c5590] == NULL` return a null sound object, otherwise call the original. Safe because `AddVoice3d` passes the result straight to `VoiceInfo.SetInfo` (stores it) and `VoiceInfo.PoolInitialize/PoolDeactive/PoolFinalize` null-check the field (cbz) before Dispose; `VoiceInfo.SoundObject` has no other users. The guard self-disables if the two code words at cri+0x59cd8 / 0x59d28 do not match. Result for an affected client: that 3D voice is not played (no sound object) and the battle continues, instead of SIGSEGV. It does NOT fix the missing ACF itself (no audio on such a client); that root cause is still open.
* Patcher: `KF_NATIVE_HOOKS` default entry `(8, 0x1BDBEFC, "f44fbea9fd7b01a9fd430091")` in scripts/patch-il2cpp-endpoints.py (active with KF_NATIVE=1); `scripts/build-kfpatch.sh` accepts `KF_CRI_TEST=1|2` (test-only builds). Slot 8 is unused by the diag hooks (1-7) and caves (16+).

## 2.11.804: fail-safe veneers + B1 root cause (2026-11-06)

### B1 (803 run 1 crash at HomeScene, il2cpp 0x121C610, fault 0x126)
* Site: il2cpp liveness traversal (per-reference check at 0x121C5E8, `ldrh w21,[x8,#0x126]` with klass == 0), reached from il2cpp_unity_liveness_calculation_from_root/_statics called by libunity (UnloadUnusedAssets style) ~2 s after HomeScene.
